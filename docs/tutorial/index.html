From one job to a cluster in 15 steps

How to write process steps, define them in SQL, trigger and follow runs, track items through a flow defined in Java, change that flow while it runs, and run several deployments on one database: on Quarkus with CDI, or with the plain Java engine.

First draft, generated by Claude (AI) with the project's initiator. It describes the proof of concept on branch poc-impl (version 0.0.2-SNAPSHOT) and changes with the review.

Step 1Build the framework

dtp isn't published to a Maven repository yet. Build it once from branch poc-impl so the modules land in your local repository.

The build runs the same quality gates on every module: Checkstyle, compiler warnings as errors, Apache RAT, JaCoCo (70 % lines), Maven Enforcer and ArchUnit. A green build means all of them passed.

ModuleUse it for
dtp-apiThe types your process steps use. No dependencies.
dtp-coreThe engine on plain JDBC (PostgreSQL, H2). Usable without CDI.
dtp-cdiStarts the engine with the CDI container. The dependency for Quarkus and other CDI runtimes.
dtp-examples/trade-appThe complete example of this tutorial on Quarkus.

Step 2Add dtp to a Quarkus app

Add dtp-cdi next to a datasource. Use Hibernate ORM (or quarkus-narayana-jta) so a JTA transaction manager is available: then your JPA changes and the item routing commit in the same transaction.

Every deployment that contains the library joins the cluster when it starts. The database is the only coordination point; there is no broker and no extra service.

Without JTA dtp falls back to plain JDBC transactions. It still coordinates correctly, but your own database work doesn't join the engine's transaction.

Step 3Configure (optional)

All settings have defaults. The namespace defaults to quarkus.application.name: all deployments with the same namespace form one cluster.

Durations accept ISO-8601 (PT5S) or the short form (500ms, 5s, 1m, 2h). The full list is in the settings reference.

Step 4Write your first job

A job is a CDI bean that implements JobHandler<P, R>: P is the type of its run parameters, R its typed result. This one has neither, so it uses NoParams and DefaultOutcome.

execute is called on exactly one node per trigger. It runs as one fenced unit of work: if this node loses its lease meanwhile (for example after a long pause), the commit is refused and another node redoes the run.

Step 5Define the job in SQL

Job definitions live in the database and reference the handler by its class name. Put them as Flyway scripts into src/main/resources/db/dtp-definitions. The engine applies them after its own schema, with its own history table, so your application's Flyway setup stays untouched.

That's all for a scheduled job: it now runs every night at 03:00 Vienna time, on exactly one node of the cluster. Cron expressions use the Quartz format: second, minute, hour, day of month, month, day of week. Every column with a default is listed in the definition reference.

Step 6Start the app

Start it like any Quarkus app. On startup the engine:

  1. applies its schema (dtp_* tables, history table dtp_schema_history),
  2. applies your definitions (dtp_definition_history),
  3. finds all process step beans and validates them,
  4. registers the node and takes part in the leader election.

The leader plans the runs: cron slots, ASAP and inbox triggers. Any node with the handler class claims and executes them. Correctness never depends on the leader: all its actions are idempotent or conditional.

Step 7Track items through a flow

Most business processes move data through several steps. dtp tracks each piece of data as an item: it knows which step's inbox holds the item, and records every hand-over in the item's journey. First, the entity declares its item type once:

The name "trade" is what's stored, so you can rename or move the class later. The id type can be UUID, Long, Integer or String.

The import is a job with typed parameters and a typed result. It tracks new trades and reports a signal for each: what happened, not where the trade goes next. The flow (step 9) decides that.

The second argument of track is the business key. You use it later to look up the journey of a trade. A signal is any enum that implements Signal; the optional second argument of signal is a reason the next step can read (item.arrivalReason()).

Step 8Process items one by one

For steps that handle one item at a time, implement ItemProcessor<E, ID>. The framework iterates the inbox, forms batches (each batch is one fenced transaction), stops softly on request and derives the run outcome. Your code reports what happened with each item:

Call exactly one of these per item. If process returns without any of them, the item counts as a technical failure.

CallEffectJourney entry
signal(signal[, reason])The flow decides: into the inbox of another step, back to an earlier step, into another flow, complete or discardROUTED, ROUTED_BACK, COMPLETED, DISCARDED
routeTo(Step.class), routeBack(Step.class, reason)Manual routing without a flow: into the inbox of that step's jobROUTED, ROUTED_BACK
defer(duration, reason)Keeps the item in this inbox until the delay has passed. Not a failureDEFERRED
fail(reason)Business failure: retried according to the job's retry policyFAILED, RETRY_SCHEDULED
complete()Ends the journey successfullyCOMPLETED
discard(reason)Ends the journey without completing itDISCARDED

@ItemProcessing is optional: batchSize (default 100), parallelism (default 1; batches run in parallel on virtual threads and never get the same items) and includeDeferred (also hand over deferred items that aren't due yet).

Step 9Define the flow

The flow connects the steps: for each signal of a step, where the item goes next. It's a CDI bean; its name is derived from the class (TradeFlow becomes trade-flow):

TargetEffect
to(Step.class)Into the inbox of the step
back(Step.class)Same, recorded as ROUTED_BACK (a loop: give the target a max_item_visits)
toFlow(OtherFlow.class)Into the entry step of the other flow's active version
complete(), discard()Ends the journey (the signal name is the reason of a discard)
onResult(Status.X, Step.class)Not for items: starts a run of the step when a run ends with that typed result

At startup the definition is validated and stored in the database as a flow version, identified by a hash of its content: the same definition on three nodes is one version, a changed definition is a new one. The jobs of the steps are generated if they don't exist; item processors get an inbox trigger. Only the entry step needs a definition in SQL, because its trigger is your decision:

To change a generated job (retries, lease, a loop limit), add a new revision in SQL as for any other job. Without a flow, steps can still route manually with routeTo and jobs can be chained with transitions (dtp_transition, see the reference).

Step 10Trigger a run from your code

Inject JobEngine. The compiler checks that the parameters match the handler's P: trigger(TradeImport.class, "2026-11-14") doesn't compile.

The trigger joins the caller's transaction; the run starts after the commit. For triggers that may arrive twice (a callback, a file), pass an idempotency key. The second call returns the existing run with newlyCreated = false:

The job's concurrency_policy decides what happens while a run of the job is pending or active: SKIP records a skipped run, QUEUE_ONE keeps at most one waiting run, QUEUE_ALL queues every trigger.

To start a flow for an entity outside of runs, e.g. in a REST resource, fire a CDI event. It joins your transaction: the trade is tracked and waits in the inbox of the entry step.

FlowEvent.signal(item, signal) is the event alternative to item.signal(signal), e.g. for a helper bean that doesn't hold the item.

Step 12Change a flow while it runs

The database holds what's executed. Operators can change it without a deployment, every change is recorded with who, when and why, and it applies to the whole cluster with the next signal.

ActionEffect
Deploy a changed TradeFlowNew version, activated automatically, unless an operator activated a version manually: then it's a candidate. Restarts and nodes of an older release never switch back
Activate a versionAlso an older one (switch back), optionally from a point in time. Refused if no active node can run one of its steps
Override a hopOne step + signal goes somewhere else, for all versions, optionally until a point in time
Migrate queued itemsItems keep the version they started with (pinning). Migration moves waiting items to another version (journey MIGRATED)

FlowQueries shows versions, activations and overrides, and generates a Mermaid diagram from the database, so it shows what's actually executed. With dtp.flows.export=mermaid every node writes all flows to target/dtp-flows.md at startup, with a validation (unrouted signals, unreachable steps, steps no node can run, loops without a visit limit). Step 13Handle failures

dtp separates two kinds of failure, so business problems and broken infrastructure don't get mixed up:

Business failureTechnical failure
CauseYour code calls item.fail(reason)process(item) throws an exception
JournalFAILED, kind BUSINESSFAILED, kind TECHNICAL, exception class and a hash of the top stack frames
Other items of the batchNot affectedThe batch is rolled back and processed again item by item, so only the failing item is affected (journal entry REPROCESSED for the others)

Both are retried according to the job: retry_max retries, the n-th one after n × retry_backoff. After the last retry the item waits in state WAITING_FOR_DECISION (journal ESCALATED) and the run finishes with COMPLETED_WITH_ISSUES. The same happens when an item enters a job's inbox more often than its max_item_visits.

Slice 1: the decision request that lets a person retry or discard the item is the next step; for now the item waits.

Step 14Run it as a cluster

Start several instances on the same database. The example has scripts that start an H2 server (local connections only) and three nodes on ports 8081 to 8083:

Kill a node with kill -9 while it works. Every run holds a lease on its job. When the lease expires, the leader takes it over and increments the fencing token, and another node reruns the run. A late commit of the old node is refused, because its token no longer matches:

In the demoObserved
kill -9 of the node enriching 2,000 tradesAttempt 1 had committed 50 items, attempt 2 on another node the remaining 1,550
kill -9 of the leaderAnother node was elected after about 3 s
A new node joinsIt claims runs right away
End state2,400 of 2,400 items completed, exactly one COMPLETED entry per item
Slice 2: 1,200 trades routed by signalsOne flow version registered by the first node and reused by the others, 900 completed and 300 routed back, all 1,200 completed after the re-import

A normal shutdown drains the node: its runs stop softly after the current batch (outcome DEFERRED if work is left), it hands over the leadership, and another node continues.

Exactly once applies to what your step commits to the database. Calls to external systems (sending a file, a mail) can repeat after a takeover, so give them an idempotency key, e.g. a deterministic file name.

Step 15Use the engine without CDI

dtp-core has no framework dependencies. Build the engine yourself and provide the steps via the StepRegistry SPI:

Without a Transactions implementation the engine uses plain JDBC transactions bound to the thread. The core's own tests run three such engines in one JVM on a shared in-memory H2 database.
