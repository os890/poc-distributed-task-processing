## Ubiquitous Language (proposal)

Earlier mission versions used working names (marked `*`). This design proposes the following terms and uses them
consistently, and the mission has been updated to them. **They still need to be confirmed [DQ-1].**

| Working name (mission) | Proposed term | Notes |
|------------------------|---------------|-------|
| job definition | **Job** | What runs, when, and what comes next. Lives in the DB. |
| job run | **Run** | One execution of a Job. Several *attempts* are possible (takeover, retry). |
| task / "task runner" | **Process Step** (code: `ItemProcessor` or `JobHandler`), **Run** (execution) | "Task" is **not** used as a domain term. It is overloaded (Jakarta Concurrency, schedulers), and Job → Run → Work Package covers the needed levels. Alternative: Job → **Task** → Work Package. |
| work package / packet | **Work Package** | "Batch" and "Chunk" are avoided because they collide with Jakarta Batch terms. |
| flow instance | **Flow Instance** | Groups runs of one end-to-end process (business key, e.g. business date). |
| consistency window / time-window | **Collection Window** (definition) + **Window Occurrence** + **Cut-off** | The window exists so that the *collector* job can collect without other jobs running. |
| time slot | **Processing Slot** | When a job may process. |
| `PARTIAL*` | outcome **`COMPLETED_WITH_ISSUES`** | Run finished, but some items/packages need attention. |
| `CARRIED_OVER*` | outcome **`DEFERRED`** | Slot end or limit reached. The remaining work waits for the next slot. |
| `AWAITING_DECISION*` | state **`WAITING_FOR_DECISION`** | Same term for runs, items, packages and window occurrences. |
| `CANCEL_REQUESTED*` | state **`STOPPING`** + `StopReason` | One soft-stop mechanism for `CANCEL`, `SLOT_END`, `LIMIT_REACHED`, `WINDOW`, `DRAIN`, `LEASE_LOST`. |
| `park(reason)` | **`escalate(reason)`** | Creates a decision request (see DD-5). |
| final item states | **`COMPLETED`**, **`DISCARDED`** | `FAILED` is not final: a failure leads to a retry or a decision request. |
| item `PENDING`, `PARKED` | **`QUEUED`**, **`WAITING_FOR_DECISION`** | Parking is an escalation to the business team. |
| run `CLAIMED`, `ABANDONED` | **`RUNNING`**, **`WAITING_FOR_DECISION`** | Claiming starts the run directly. The takeover policy `ABANDON` creates a decision request (`RETRY` / `FAIL` / `SKIP`). |
| join | **run join** vs. **item join** | *Run join*: a job waits for several jobs of the same flow instance (DD-9). *Item join*: the step that receives a forked item after all its branches (DD-22). |
| `ValidateOrder`, `ShipOrder`, … | **`OrderValidation`, `OrderShipment`, …** | Process steps are named after the business activity, not as commands (DD-28). |

**Result status vs. outcome.** A handler returns a typed **result status** (`R`, e.g. `DefaultOutcome.SUCCESS`,
`ImportOutcome.NO_DATA`). The engine sets the framework **outcome** (`RunOutcome`: `SUCCEEDED`,
`COMPLETED_WITH_ISSUES`, `DEFERRED`, …), e.g. `COMPLETED_WITH_ISSUES` when items of the run wait for a decision.
Transitions match on either one: `on_result_status = 'SUCCESS'` or `on_outcome = 'SUCCEEDED'`.

### Glossary

| Term | Meaning |
|------|---------|
| Lease | Time-limited right of one node to execute the active run of a job. Renewed while the run is alive (DD-1). |
| Fencing token | Number that increases with every lease acquisition and expiry. Writes of a node with an old token are rejected, so a "zombie" node can't commit. |
| Quiesce | Soft-stopping the paused steps of a collection window and waiting until they are idle. |
| Cut-off | End of a window occurrence's data. The next occurrence starts there, so occurrences never overlap. |
| EOD | End of day: the daily processing of a business day. |
| Keyset pagination | Reading the next page "after the last seen key" instead of `OFFSET`, which stays fast for large inboxes. |
| Process step | A CDI bean that processes items (`ItemProcessor`) or runs (`JobHandler`). One step corresponds to one job definition. |
| Projection | Read model derived from the journal by an elected projector (CQRS). Clients only read it (09). |
| Jam score | 0–100 per step: how far the step lags behind its expected throughput. Only steps that should be processing can be jammed (09 §9.4). |

## Proposed Design Decisions

| # | Decision | Rationale |
|---|----------|-----------|
| DD-1 | **The lease belongs to the Job, not the Run** (`dtp_job_lease`, one row per job). Claiming a run = conditionally acquiring the job's lease. | "At most one active run per job" becomes structural. It is portable (no partial indexes, which H2 lacks), and fencing tokens are per job, so a token can never be reused. |
| DD-2 | **The DB clock is the only clock** for leases, heartbeats, slots and cut-offs. The `DbClock` port reads the DB time and binds it as a parameter (see 03), so tests can control the time. | Node clock skew cannot break lease expiry or window boundaries. |
| DD-3 | **Explicit leader election** through a pluggable `LeaderElection` SPI (JDBC default with its own `dtp_leader` table, see 03 §3.4 and 05 §5.10). Only the leader of the role `housekeeping` runs the planner, reaper and window coordinator. Claiming and executing happen on all nodes. **Correctness never depends on the leader**: every leader action is idempotent or conditional, so two nodes that both believe they are leader cause duplicate work, never duplicate effects. | DB load does not grow with the number of nodes. Any node can take over. The leader is an optimization, not a safety mechanism. |
| DD-4 | **Finishing a run is one fenced transaction**: run state + outcome, transitions/successor runs, join arrivals, lease release. | No lost successors and no double triggers on a crash between steps. |
| DD-5 | **One mechanism for human intervention: the Decision Request.** It is used for retries exhausted, loop limit exceeded, `escalate()`, takeover policy `ABANDON`, window quiesce timeout and collector failure. | Fewer concepts: business users and operators work through one inbox with typed options. |
| DD-6 | **Continuous (ASAP) jobs use long-lived runs with cycles.** The engine calls `execute` repeatedly within one run (with idle backoff) until a stop signal arrives (slot end, window, drain, cancel, lease lost). | Avoids millions of empty run rows. Lease ownership stays stable. Each run maps to a clear period (e.g. "today's slot"). Cycle statistics are aggregated in the run info. Alternative: a new run per cycle **[DQ-2]**. |
| DD-7 | **Item references are stored as `(item_type, ref_id, ref_version)` strings.** `item_type` is the name of the entity's `ItemType` descriptor (DD-20), and `ref_id` is encoded by an `IdCodec` (UUID, Long, …). | Type-safe in Java, and refactoring-safe in the DB (the FQCN is not persisted). |
| DD-8 | **CQRS-lite for items**: `dtp_item` holds the *current* state (updated), and `dtp_item_event` is the *append-only journey* (insert-only, batched, partition-ready). | Fast inbox queries plus a complete audit trail. Neither has to compromise the other. |
| DD-9 | **Joins are serialized by a join-instance row lock** (`SELECT … FOR UPDATE` on `dtp_join_instance`) plus a unique run key. | Prevents the classic READ COMMITTED race where two concurrent arrivals each see only themselves and nobody fires. |
| DD-10 | **Job definitions are versioned**: every change creates a row in `dtp_job_revision`, and runs reference `(job_id, revision)`. | History is immutable, and red/green versions can run against different revisions without ambiguity. |
| DD-11 | **Polling with adaptive backoff** in the PoC. DB push notifications (e.g. PostgreSQL `LISTEN/NOTIFY`) are a later optimization behind the same port. | Simple, portable, and works on H2. |
| DD-12 | **Transaction boundaries**: framework state changes run in short transactions of their own. Business work runs in *unit-of-work* transactions (one per inbox batch or work package) that also flush item routing. The **fence check is the last statement** before the commit (03 §3.4), so the lease row is locked only for the commit itself. | No lock is held during business work (mission principle 6), routing stays atomic with business changes (D20), and renewals are never blocked by a running batch. |
| DD-13 | **Claiming locks the job-lease rows, not the run rows** (`FOR UPDATE OF lease SKIP LOCKED`, at most one candidate per job). A lost race is a normal, silent outcome (0 rows, a skipped row, or a classified lock/deadlock/serialization exception → rollback, try the next candidate or the next poll). See 05 §5.2. | No two nodes compete for the same lease row with `SKIP LOCKED`. Only one row lock per job means no deadlock cycles. The claim transaction is isolated, so losing a race affects nothing else. |
| DD-14 | **Desynchronized nodes**: a random start offset per node, ±25% jitter on every poll and leader attempt, backoff with full jitter after conflicts, adaptive idle backoff, and per-node shuffling of candidates on dialects without `SKIP LOCKED`. The random seed is configurable (`dtp.random.seed`): random in production, fixed in tests for reproducible race scenarios. | Prevents thundering herds with many nodes (e.g. 200 nodes don't poll at the same instant) and keeps idle DB load low. |
| DD-15 | **App definitions in a separate Flyway location** (`db/dtp-definitions`, history table `dtp_definition_history`), applied by the engine **after** its own schema migration. See 07 §7.1. | Definitions need the `dtp_*` tables first. The app's own Flyway setup stays untouched, and definitions remain SQL-based and red/green-safe (D23). |
| DD-16 | **Approval requests with quorum**: decision requests of kind `APPROVAL` need `requiredApprovals` distinct `APPROVE` votes. One `REJECT` rejects. One vote per user, all votes audited. No segregation-of-duties rule for now. | Four-eyes principle for exceptional cases, e.g. unusually large orders (08). |
| DD-17 | **`Items` is injectable**, so application code can track and route items outside a run, in its own transaction. | Incoming data (e.g. orders via REST) enters the flow atomically with its persistence. |
| DD-18 | **`item.defer(delay, reason)`**: the item stays queued in the same inbox until `next_attempt_at`, without counting as a failure. | Waiting for external events (e.g. a supplier delivery) without a separate concept. |
| DD-19 | **Decision results go back to the requesting job**: the decided item is re-queued in that job's inbox, and the handler reads `item.approval()` / `item.decision(Class)` and routes it. | Routing decisions stay in typed handler code, not in DB configuration. |
| DD-20 | **Typed item descriptor `ItemType<E, ID>`**, declared once per entity as a constant (`Order.ITEM`), instead of an `@ItemType` annotation. | `item.ref().id()` is typed (no `id(UUID.class)` cast), and inbox, refs and packages are bound to the entity type at compile time. |
| DD-21 | **Durations are stored as ISO-8601 strings** (`PT4H`) instead of SQL `interval`. | Definition scripts are identical for PostgreSQL, H2 and future dialects. |
| DD-22 | **Fork/join on item level**: the fork is declared at a CDI injection point (`@Inject @ForkTo(value = {A.class, B.class}, joinAt = J.class) Fork screening`) and validated at bootstrap. `item.fork(screening)` creates one branch row per branch step (`dtp_item_branch`). Branches run in parallel (different steps, different leases, possibly different nodes). The item row lock serializes completions, so the last branch queues the item at the join step, which reads typed `branchResults`. | Independent steps (e.g. credit, plausibility and address checks) run in parallel without the handler coordinating threads or nodes. Wiring stays CDI-style and is checked by the container. |
| DD-23 | **Lanes**: an `ItemLane` (priority + weight) set when the item is tracked and kept for its whole journey. Every inbox serves lanes by priority, and the weights prevent starvation. | Grouping such as VIP vs. standard customers without separate jobs per group. Metrics per lane. |
| DD-24 | **Responsible teams** for decision and approval requests (`Responsibility`, matched against the MP JWT `groups` claim). Only members see the request and can vote or decide. | Decisions go to the department in charge (e.g. purchasing per product category, customer care). |
| DD-25 | **Parallel batches within one step** (`@ItemProcessing(parallelism = …)`, or `forEachBatchInParallel` in a `JobHandler`): virtual threads of the owning node, one fenced transaction per batch. | Slow steps (e.g. external scoring) scale within one step without breaking the single-run-per-job rule. |
| DD-26 | **`ItemProcessor<E, ID>` is the default way to write a process step**: one `process(item)` method, while the framework does iteration, batches, transactions, soft stops and the outcome. `JobHandler<P, R>` remains for full control (packages and windows, typed parameters, jobs without items). Both extend `ProcessStep`, which is the type of all routing targets. `RunInfo` is injectable. | Ease of use: the common step needs one method instead of plumbing (inbox, batching, result). |
| DD-27 | **`includeDeferred`**: a step can look at deferred items before they are due, e.g. `DeliveryMonitoring` after every goods receipt. | Waiting items react to external events immediately, not only when their defer delay ends. |
| DD-28 | **Process steps are named after the business activity** (`CreditCheck`, `StockReservation`, `OrderShipment`), not as commands (`CheckCredit`). Job names in the DB follow the class names (`credit-check`). | DDD ubiquitous language: code, definitions, journey and REST speak the language of the business. |
| DD-29 | **Business vs. technical failures**: `item.fail(reason)` is a business failure. An exception thrown by a step is a technical failure (error type and stack hash in the journal). A failed batch is rolled back and retried item by item (poison-item isolation). Exhausted technical retries go to operations (`technical_responsible_group`, default `dtp-operator`). | One bad item never blocks its batch. Technical problems reach the people who can fix them, and the heat map can show unexpected exceptions separately. |
| DD-30 | **Monitoring as a CQRS read model**: an elected projector (leader role `projection`) derives small views from the journal and the item state every ~10 s. It recomputes the minute buckets of the last two lease durations, which is complete because no unit of work can commit later than its lease. | Cluster-wide heat map without load on the processing tables, without extra writes on the hot path, and rebuildable at any time. |
| DD-31 | **Clients read on demand**: REST snapshots and a live feed via Server-Sent Events, served by any node from the views. Alert state transitions fire CDI events (`StepCongested`, `TechnicalFailureSpike`) exactly once. | Reads scale with the number of nodes. The application decides whom to notify. |
| DD-32 | **Jam detection with status reasons**: a closed slot, an open window or a disabled job is an *expected backlog*, not a jam. `NO_CAPABLE_NODE` is always alarming. Thresholds per step are part of the job definition. | No false alarms, and real jams stand out. |
| DD-33 | **Telemetry in two layers**: per-node real-time metrics on the processing path (incl. wait-time histograms per lane) and cluster gauges exported only by the projector leader. Bounded attribute cardinality. Traces link an item's units of work across steps to the request that tracked it. | Standard tooling (OTel, Prometheus, Grafana) gets real-time signals, percentiles and end-to-end traces, consistent with the heat map. |
| DD-34 | **Journey diagram per item**: `GET /dtp/items/{type}/{businessKey}/journey/diagram` folds the item's journal entries into a graph of only the steps it passed (incl. branches, decisions, packages, back-routes, current position) and returns Mermaid source or JSON. Labels are escaped, and technical details are only shown to operators. | Users can check how one item was processed, without reading tables. No rendering library and no UI in the framework: Mermaid renders in browsers, tickets and wikis. |

## Open Design Questions

- **DQ-1** Confirm the ubiquitous language above, especially **Run vs. Task** and **Collection Window**.
- **DQ-2** Continuous jobs: long-lived run with cycles (DD-6), or a new run per cycle (simpler semantics, more rows)?
- **DQ-3** Can the same `ItemRef` be tracked **several times at once** (e.g. the same customer changed twice and
  forwarded in two windows)? Proposal: unique per `(item_type, ref_id, ref_version)`, so a new version means a new tracked item.
- **DQ-4** Should the retry scope (item vs. package) be a property of the **Job** (proposal) or chosen per call in the handler?
- **DQ-5** Handler binding: can **one handler class serve several Jobs** (e.g. with different parameters)? The DB allows
  it (handler FQCN per job). The API then needs `ctx.job()` to distinguish them. This relates to Q-10 in the mission.
- **DQ-6** Item type resolution for `ItemProcessor<E, ID>`: the proposal is the entity's `ItemType` constant, found by
  convention and validated at bootstrap. An alternative is a CDI producer of `ItemType<E, ID>`.
