## The Idea in Five Lines

- A **DB-coordinated workflow engine** for CDI developers on MicroProfile runtimes and Quarkus. It needs no extra
  infrastructure: the database is the only coordination point.
- **Job definitions live in the DB**, and every deployment that contains the library joins the cluster automatically.
- **Each planned run happens once per trigger**, on exactly one node. Crashed or hanging nodes are detected, and
  another node takes over safely.
- **Every data item is traceable**: which steps it passed, where it was routed back, who approved what, and in which
  package it left the system. A **journey diagram** shows the path of a single item, and a **live heat map** and
  telemetry metrics show where the flow jams or fails.
- **Simple by default** (a handler class + one definition row), **powerful on demand** (parallel branches, approvals,
  collection windows, time slots, lanes), with a **type-safe** API.

## Guarantees – Precisely

| Guarantee | How |
|-----------|-----|
| A trigger occurrence creates **at most one run** | Unique run key per trigger occurrence (02 §2.3, 03 §3.4) |
| A job has **at most one active run** in the cluster | One lease row per job, conditional acquisition (DD-1, DD-13) |
| **Committed DB effects** of a unit of work happen **exactly once** | Fenced commit: a node that lost its lease can't commit, and its uncommitted work is redone by the new owner (DD-12) |
| **Calls to external systems** (sending a file, shipping, mails) are **at-least-once** | They can't be rolled back: after a takeover they may repeat. Use idempotency keys (e.g. order number, deterministic file name), as in the samples |
| Correctness **never depends on the leader** | All housekeeping actions are idempotent or conditional (DD-3) |

## Open Questions

- Mission **Q-1**: who flips the red/green activation switch, and what does the old color still finish? The first
  implementation proposes an answer (slice 21, to be confirmed in the review): an administrator or the pipeline
  switches, and the old color finishes only the current unit of work of its runs.
- Design **DQ-1…DQ-6** in [docs/design/README.md](docs/design/README.md#open-design-questions): final terms
  (Run vs. Task), the model for continuous runs, item uniqueness per version, the retry scope, one step for several
  jobs, and how an `ItemProcessor` finds its item type.

## First Implementation

Branch `poc-impl` contains a first implementation (slice 1) with a runtime demo on three Quarkus nodes, flows with
signals, versions and overrides (slice 2), decision requests and approvals (slice 3), fork/join on item level
(slice 4), decision fallbacks with domain events (slice 5), flow instances with run joins (slice 6), business
calendars with processing slots (slice 7), work packages with item and time limits (slice 8), collectors that
hand their packages over to other jobs (slice 9), collection windows (slice 10), the monitoring read model with
heat map, jam detection, alerts and a live feed (slice 11), the journey diagram per item (slice 12), telemetry
metrics and traces with OpenTelemetry (slice 13), acknowledgements of sent work packages (slice 14), lane weights
with flow versions per lane (slice 15), the REST adapter with MP OpenAPI and MP JWT roles (slice 16), the tests
of the engine on PostgreSQL 17 (slice 17), continued deferred runs in flow instances (slice 18), decisions
requested by job runs, e.g. a four-eyes sign-off of an end of day (slice 19), cancelling flow instances, e.g.
an end of day started by mistake (slice 20), red/green deployments with an activation switch (slice 21), the
test support `dtp-test` for applications, a JUnit 5 extension with simulated nodes and a clock the test moves
forward (slice 22), the domain events of the execution (runs, leases, nodes, windows, packages, jobs; slice 23),
red/green follow-ups (runs the old color holds, an active color without live node, slice 24), and corrections of
decisions and journeys (slice 25): see [IMPLEMENTATION.md](IMPLEMENTATION.md).
