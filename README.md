## The Idea in Five Lines

- A **DB-coordinated workflow engine** for CDI developers on MicroProfile runtimes and Quarkus. It needs no extra
  infrastructure: the database is the only coordination point.
- **Job definitions live in the DB**, and every deployment that contains the library joins the cluster automatically.
- **Each planned run happens once per trigger**, on exactly one node. Crashed or hanging nodes are detected, and
  another node takes over safely.
- **Every data item is traceable**: which steps it passed, where it was routed back, who approved what, and in which
  package it left the system. A **journey diagram** shows the path of a single item, and a **live heat map** and
  telemetry metrics show where the flow jams or fails.
- **Simple by default** (a handler class + one definition row), **powerful on demand** (parallel branches, approvals,
  collection windows, time slots, lanes), with a **type-safe** API.

## Guarantees – Precisely

| Guarantee | How |
|-----------|-----|
| A trigger occurrence creates **at most one run** | Unique run key per trigger occurrence (02 §2.3, 03 §3.4) |
| A job has **at most one active run** in the cluster | One lease row per job, conditional acquisition (DD-1, DD-13) |
| **Committed DB effects** of a unit of work happen **exactly once** | Fenced commit: a node that lost its lease can't commit, and its uncommitted work is redone by the new owner (DD-12) |
| **Calls to external systems** (sending a file, shipping, mails) are **at-least-once** | They can't be rolled back: after a takeover they may repeat. Use idempotency keys (e.g. order number, deterministic file name), as in the samples |
| Correctness **never depends on the leader** | All housekeeping actions are idempotent or conditional (DD-3) |
